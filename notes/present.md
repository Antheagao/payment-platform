## The brief (2026-10-28)

The repository answers a software engineer technical exercise: a simplified payment processing platform with a backend API, a merchant dashboard, and at least one asynchronous workflow.
The exercise grades system design, code quality, architectural decisions, operational thinking, and tradeoffs; it prefers a small, well-reasoned slice over a broad, shallow one.
The requirements are restated in our own words in `docs/requirements.md`, each traced to where it lives and its status.

The base of the project was requested with these requirements; they are recorded here so nothing drifts:

1. Match the hiring team's Microsoft stack: C# and .NET for APIs, services, and integration layers; Azure (Functions, App Service, Logic Apps, Storage, Azure SQL, monitoring); SQL with stored procedures; Python for automation only if a data pipeline needs it.
   Preferred extras they list: Azure DevOps CI/CD, Terraform or Bicep, event-driven messaging, ETL.
2. Frontend: Next.js, TypeScript, and Tailwind CSS.
3. A `frontend/` folder and a `backend/` folder at the root.
4. A `.claude/` folder with `CLAUDE.md` plus testing, CI/CD, security, architecture, and design guides drawn from the claude-brain repository.
5. Built through the batch loop, with a commit and a push after each task or every few tasks, so the history shows the progress.
6. Database: SQL Server (the owner's choice on 2026-10-28, over the usual PostgreSQL default, to match Azure SQL).
7. A public GitHub repository.

A second request the same day added:

8. One easy command that starts everything, with every download it needs listed.
9. Fully functional without any paid service.
10. Able to load sample data and sample dashboards, for a live demo or for a reviewer who downloads it to see what was built.

A third request the same day added:

11. Screenshots of the pages and GIFs of the dashboard in use, the frontend checked in a real browser, and its design brought up to current practice (layout, color values) following the repository's frontend overlay and the claude-brain `frontend-ui` guide.

## How it runs

- API alone, from `backend/`: set `ConnectionStrings__Payments` (or `dotnet user-secrets set ConnectionStrings:Payments ... --project src/PaymentPlatform.Api`), then `dotnet run --project src/PaymentPlatform.Api`; it listens on `http://localhost:5080`.
  Without a database, `/health/live` is 200 and `/health/ready` is 503 within its 3 s deadline, so the dashboard (which waits 5 s) shows "API not ready" rather than "API unreachable".
- Worker alone: the same connection string, then `dotnet run --project src/PaymentPlatform.Worker` (health on `http://localhost:5081`).
- Whole stack: `docker compose up --build`, with no `.env` and no other setup: SQL Server on `localhost,14333`, a one-shot bootstrap that creates the `payments` database and the `payments_app` login, the Aspire dashboard on `http://localhost:18888`, the API on 5080, the worker on 5081, the dashboard on 3080 through the Caddy `edge` (the dashboard's own container publishes no port); `docker compose down` stops it, `down -v` drops the database too.
  The local passwords (`LocalOnly_Admin_2026!` for `sa`, `LocalOnly_App_2026!` for `payments_app`) and every host port have defaults in `docker-compose.yml`; a gitignored `.env` overrides them (`.env.example` lists the variables).
  `sh scripts/check-stack.sh` waits until every service answers and prints the URLs; the CI `stack` job runs exactly that after `docker compose up --build --detach --wait`.
  The API seeds the demo merchant and its 280 sample payments (`Demo__Seed`): log in with `demo@example.com` / `LocalOnly_Demo_2026!` at `POST /api/v1/auth/login`; with no `JWT_SIGNING_KEY` in `.env` it signs with a key made at startup, so tokens end when it restarts.
  `check-stack.sh` also fails if the API or the worker logs a warning while starting.
  `webhook-receiver` (`scripts/webhook-receiver.mjs` on `node:22-bookworm-slim`, `http://localhost:8090/events`) stands in for the demo merchant's server: it verifies each delivery's signature with the shared local-only secret, drops repeated ids, and answers `503` to payments whose reference starts with `webhook-fail`, so retries show.
  Verified 2026-10-28 from an empty volume: both migrations applied, the demo seeded, no startup warnings, login, `/me`, the 401, 400, 415, and 429 answers, and a fixed key surviving a restart.
- The dashboard is part of compose on `http://localhost:3080`, with `API_ORIGIN` and `WORKER_ORIGIN` pointing at the API and worker inside the network; alone, `cp frontend/.env.example frontend/.env.local` and `npm run dev` from `frontend/` (same port).
